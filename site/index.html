Project plans in plain markdown

Plain-markdown project plans that scale from a todo list to a programme of thousands of teams.

Made for humans and AI agents working on one plan. People edit the files in any editor; agents edit the same files with the pmd tools. Either can own a project, promise a date or wait on the other.

Why

The problem

Large undertakings need many interdependent projects to come together on strict dates, with milestones, decision gates and sign-offs. Different people, teams and companies own the parts, each with their own tools.

Ticket trackers

Show what, but timelines and cross-team dependencies are bolted on.

Scheduling tools

Show when, but are heavy and centralised: one file, one owner, everyone else gets a PDF.

Text todo lists

Are what people actually write, but they say nothing about time.

projectmd keeps the todo list and adds just enough structure to answer: when? what depends on what? who promised what to whom?

The key message

Humans and agents, one plan

People edit the files in any editor; agents edit the same files with the pmd tools. Either can own a project, promise a date or wait on the other.

Human

Writes plain markdown

  • Edits in any editor, reviews in git
  • Owns decisions: open items that delay whatever waits on them, so the delay shows in the forecast
  • Asks for a date with by: on their own link line
.mdshared file
Agent

Uses the pmd tools

  • pmd fmt rewrites a file into one canonical form, so edits give small diffs
  • pmd ready lists open items that may start now; claim one with after: <today>
  • Diagnostics come one per line with a fix: hint, or as JSON
  • Edits only what it owns

Tested in two simulations: a 1961–69 lunar programme with 11 persona agents over 19 rounds, and a mixed team of two humans and six agents shipping a library release.

Concepts

The idea

Every file is a project

Its list items are tasks and milestones. A todo list is already a valid plan.

A link makes a sub-project

The linked file can live anywhere a link can point.

Owners promise, parents ask

A child states a Commitment: and dated milestones. A parent states what it needs with by: on its link.

Only declared dates cross files

Forecasts never do. A child that cannot keep its promise moves it, and that move is the signal.

Contract states are live

Computed from the two files: requested, agreed, disputed, overdue, delivered. Nothing is stored.

Grow gradually

To turn a task into a sub-project, replace its title with a link. Nothing else on the line changes.

Scale

How it scales

Locality

Any view reads one file plus its direct links, whether the graph has 10 projects or 100,000.

Distributed storage

A sub-project can live on disk, in git, on a shared drive, or at a URL, kept by its own team with its own tools.

Access control is external

The store decides who reads what. In the format, a project only decides what it shows the level above.

No special root

Every project is the top of its own view.

Measured on synthetic trees (release build, Apple M2): pmd check takes about 3 ms at 1,111 files and at 111,111 files. A deep check is linear: 11 s for 111,111 files. Details in BENCHMARKS.

Tools

Tools

Tools are reference implementations; the format is the product. Anyone can write others.

CLI: pmd

Parse, check, schedule, list ready work, format and tree.

Web Gantt viewer

Static JavaScript plus WebAssembly, no build step. Open the lunar programme.

Rust library

pmd-core is the parser and validator; it also builds to WebAssembly.

pmd
usage: pmd parse FILE
     | check FILE... [--deep] [--strict] [--today D] [--json]
     | schedule FILE... [--today D] [--json]
     | ready FILE... [--deep] [--owner NAME] [--today D] [--json]
     | fmt FILE... [--check]
     | tree FILE... [--depth N] [--today D]
