Project plans in plain markdown

Plain-markdown project plans that scale from a todo list to a programme of thousands of teams.

Made for humans and AI agents working on one plan. People edit the files in any editor; agents edit the same files with the pmd tools. Either can own a project, promise a date or wait on the other.

Why

The problem

Large undertakings need many interdependent projects to come together on strict dates. Different people, teams and companies own the parts, each with their own tools. Ticket trackers show what but bolt timelines on; scheduling tools show when but are centralised; text todo lists are what people write, but say nothing about time.

projectmd keeps the todo list and adds just enough structure to answer: when? what depends on what? who promised what to whom?

The idea

Three laws

Every file is a project; a link to another file makes it a sub-project. Three laws shape every other rule, and nothing in the format contradicts them.

Ownership

Every file has one owner. You write only what you own.

Buys: no merge conflicts between owners, and a clear author for every promise.

Locality

Between owners, only declared dates cross a link. Forecasts never do.

Buys: privacy (a parent sees promises, not plans) and scale (a view reads a file and its direct links).

Derivation

Nothing is stored that can be computed.

Buys: no stored state to go stale or synchronise; any tool, given the files, gets the same answer.

Read more: the design, the format.

The promise protocol

Parents ask, owners promise

Between a parent and a child there is one exchange. The parent asks with by: on its link line. The child promises with a Commitment: or a dated milestone. The pair is a contract; its state is derived, and every state names whose move it is.

StateMeaningWhose move
deliveredchild has Done:, or the milestone is tickednobody
unknownchild cannot be readparent: fix the link or access
disputedpromise later than by: (whether or not by: has passed), or milestone cancelledparent: accept, re-plan or talk
overdueby: passed, not delivered, and no promise later than by:child: deliver, or move the promise
requestedby: set, no promisechild: answer
agreedpromise on or before by:child: deliver

Each side edits only its own file; agreement is reached outside the format and the files record the outcome. A dispute sits with the parent because the child's promise is a fact about what it can do, while the parent's by: is a wish.

A slip travels one level at a time

Descent stagemoves its Commitment 2027-11-30 → 12-31
→
Lunar modulereads disputed, then decides:(a) accept, by: → 12-31. Forecast still inside its Commitment, so nothing changes above.(b) forecast passes its Commitment: moves it.
→
Programme HQ(a) sees nothing change; contract still agreed.(b) reads disputed, and decides in turn.

A slip that stays inside a team's Commitment changes nothing above the team. A slip past a Commitment changes exactly one file per level. Each level sees that the level below moved, and to when, never why.

Derivation

Everything else is derived

Each of these is computed from the files when asked. None is stored, so none can go stale.

Schedule

Forecast start and end of every node, slack, conflicts. A decision someone owes delays what waits on it, a day per day.

pmd schedule bakery.md

Contract state

From the ask and the promise, one hop, shown per link.

pmd tree bakery.md

The queue

pmd ready: work to do and moves owed (decide, fix, answer, deliver), for one owner, human or agent.

bakery.md:7  DO  Test menu  owner: Noor Haddad  due: 2027-03-14

Drivers

pmd why names the one constraint that fixed an item's end. Follow it file by file to find the critical path, with no global computation.

pmd why bakery.md ^gono --deep
bakery.md:13  Go/no-go decision  forecast 2027-05-18
  <- bakery.md:11  Test menu  2027-05-18

Change events

pmd changes OLD NEW reads two versions of one file and lists what moved: a notification feed for parents and children.

pmd changes <(git show origin/main:plan.md) plan.md

The board

Kanban columns Waiting, Ready, Doing and Done, derived from after: and done:. A view, not a second system: working board-style.

pmd board bakery.md

Replan proposals

pmd replan proposes the smallest edits to a file's own dates that make it consistent, and lists the promises that would move.

pmd replan plan.md --write

Scale

How it scales

Locality

Any view reads one file plus its direct links, whether the graph has 10 projects or 100,000.

Distributed storage

A sub-project can live on disk, in git, on a shared drive, or at a URL, kept by its own team with its own tools.

Access control is external

The store decides who reads what. In the format, a project only decides what it shows the level above.

No special root

Every project is the top of its own view.

Measured on synthetic trees (release build, Apple M2): pmd check takes about 4 ms at 1,111 files and at 111,111 files. A deep check takes 0.06 s at 1,111 files and 13 s at 111,111. Details in BENCHMARKS.

The key message

Humans and agents, one plan

People edit the files in any editor; agents edit the same files with the pmd tools. Either can own a project, promise a date or wait on the other.

Human

Writes plain markdown

  • Edits in any editor, reviews in git
  • Owns decisions: open items that delay whatever waits on them, so the delay shows in the forecast
  • Asks for a date with by: on their own link line
.mdshared file
Agent

Uses the pmd tools

  • pmd fmt rewrites a file into one canonical form, so edits give small diffs
  • pmd ready lists open items that may start now; claim one with after: <today>
  • Diagnostics come one per line with a fix: hint, or as JSON
  • Edits only what it owns

Tested in two simulations: a 1961–69 lunar programme with 11 persona agents over 19 rounds, and a mixed team of two humans and six agents shipping a library release.

For kanban and agile teams

Used to kanban or agile?

A board is a view of the plan, not a second system: its columns come from the file's after: and done: lines, so you move a card by editing one line. There are no custom states; a review step is an item with an owner. The team boundary is the file boundary: flow inside, promises outside.

Tools

Tools

Tools are reference implementations; the format is the product. Anyone can write others.

CLI: pmd

Parse, check, schedule, load, ready, why, changes, replan, format and tree.

Web Gantt viewer

Static JavaScript plus WebAssembly, no build step. Weekend shading when zoomed to days, a critical path toggle, an overlap chip for owners with more than one item at once, and a legend.

Rust library

pmd-core is the parser and validator; it also builds to WebAssembly.

The tools have one job: the plan. Other tools read it. pmd schedule --rows prints one JSON line per item for resource planning; capacity, skills and cost stay outside the format.

Build and run: see the README quick start.
